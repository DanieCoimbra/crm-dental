**Autor:** Go Architect & QA Reviewer  
**Versão:** 2.0 (Atualizado para Go 1.26 + Render Native + Supabase Native Migrations)  
**Status:** Aprovado  

---

## 1. Resumo Executivo & Declaração do Escopo

### 1.1 Visão Geral
O `backend-go` opera como uma **API RESTful de Alta Performance** em Go 1.26 com Fiber v2, projetada para atender ao ecossistema SaaS Multi-Tenant da clínica odontológica (`clinics`). Toda a persistência é gerenciada via Supabase (PostgreSQL) usando GORM v2.

### 1.2 Arquitetura de Implantação e Infraestrutura (Render & Supabase)
- **Hospedagem API:** Render em ambiente nativo Go 1.26 (`render.yaml`), sem dependência de contêineres Docker local ou em produção.
- **Banco de Dados & Storage:** Supabase PostgreSQL conectado via **Supavisor Connection Pooler** (porta 5432) com sanitização de DSN.
- **Gerenciamento de Schema:** Migrações versionadas no diretório [/supabase/migrations](file:///C:/IgnisPath/Crm-Clinica/supabase/migrations) com suporte a `BIGINT GENERATED BY DEFAULT AS IDENTITY` para compatibilidade estrita com os modelos `uint` do GORM Go.

### 1.3 Objetivos e Métricas de Sucesso
- **[GO-01] Cobertura de Contexto Tenant:** 100% dos handlers privados acessam e filtram estritamente por `clinic_id` (`c.Locals("clinic_id")`).
- **[GO-02] Compatibilidade com Banco de Dados:** Mapeamento 1:1 entre os modelos GORM Go e as tabelas SQL nativas do Supabase.
- **[GO-03] Performance:** Resposta média dos endpoints abaixo de 100ms e inicialização da API abaixo de 3 segundos no Render.

## 2. Histórias de Usuário & Funcionalidades Core (Fases 0 a 4)

### US-GO-001: Autenticação Multi-Tenant & RBAC
- **Descrição:** Como usuário (Dono, Gerente, Dentista ou Recepcionista), quero autenticar via JWT para ter acesso isolado aos dados da minha clínica.
- **Critérios de Aceite:**
  - Token JWT decodificado no middleware decodifica `user_id`, `clinic_id` e `role`.
  - Perfis suportados: `owner`, `manager`, `doctor`, `receptionist`.

### US-GO-002: Prontuário Eletrônico & Odontograma (EMR)
- **Descrição:** Registro de histórico do paciente, odontograma por dente/superfície e upload de exames.

### US-GO-003: Agendamento Multi-Salas & Fila de Espera
- **Descrição:** Gestão de agenda com alocação por profissional/sala e fila de espera dinâmica.

### US-GO-004: Gestão Financeira, Orçamentos & Emissão de PDF
- **Descrição:** Emissão de orçamentos, lançamentos financeiros e geração de recibos em PDF.

### US-GO-005: Estoque Interligado & SaaS Billing
- **Descrição:** Consumo automático de insumos e controle de assinaturas da clínica.

## 3. Requisitos Funcionais do Backend Go

- **FR-GO-1:** Estruturado em **Clean Architecture** (`cmd/server/main.go`, `internal/adapters/handlers`, `internal/core/services`, `internal/core/domain`, `internal/database`).
- **FR-GO-2:** Framework web **Go Fiber v2** de alta performance.
- **FR-GO-3:** ORM **GORM v2** conectado ao Supabase Pooler.
- **FR-GO-4:** Respostas de erro padronizadas em JSON (`error`, `message`, `details`).

## 4. Implantação e Deploy Nativos (Render)

Especificação do arquivo `render.yaml`:
```yaml
services:
  - type: web
    name: dental-crm-api
    env: go
    rootDir: backend-go
    buildCommand: go build -o server cmd/server/main.go
    startCommand: ./server
    plan: free
    region: oregon
    healthCheckPath: /health
```
